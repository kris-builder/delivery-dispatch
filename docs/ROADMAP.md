# 从开工到 MVP 的路线图

这是每天的开工入口。先看本页的顺序和当前验收条件，再打开对应 Spec。业务图看[模块设计](MODULES.md)，表和索引看[数据库设计](DATABASE.md)，接口与测试约定看[工程规范](ENGINEERING.md)。

## 先定两个交付点

| 交付点 | 当场要能演示的结果 |
| --- | --- |
| **MVP · 网点直派闭环** | 同一票上门件由网点员工连续扫码实收，调度确认发布，配送员扫码领走并登记送达，收件人在手机上看到实际进度。另走一票失败待返站和网点实际收回。用 Vue、Spring Boot、MySQL 与 Flyway 跑通，实际写入可追溯。 |
| **在途增强版** | 在已能演示的上门链路上接 Redis 和 FastAPI。用模拟地图耗时实现最近位置、剩余站点和预计时段。关闭估时服务或让位置过期，仍能查实际履约。 |

沿用 Gemini 的 V1/V2 分批思路。将原路线 Day 9–10 的位置和估时列为第二个交付点，避免地图及 Python 接入拖住核心验收。真实 MySQL 的并发、回滚和逐票权限测试随对应主线写入交付。前端按已通过的工作台设计逐步实现，首轮只交付网点分拣、调度、网点配送和收件人查件。分拣首轮显示实收结果和批次统计，个人计件、作废更正和完整对账随后成组接入。

## 开工前的一轮准备

1. **确认仓库基线。** 用 `git status --short --branch` 确认工作区，`git rev-parse --verify HEAD` 确认基线。首次提交前核对已有文件、忽略项与暂存差异。基线提交完成后从具体提交开 worktree，分支用 `codex/` 开头。 [Git worktree](https://git-scm.com/docs/git-worktree) · [协作规则](../AGENTS.md)
2. **跑工具链冒烟。** 核对 `java -version`、`delivery` 目录下的 `./mvnw.cmd -v`、`node -v`、`npm -v` 和 `docker info`。POM 对齐 Java 21，Compose 与 Testcontainers 固定同一 MySQL 8.4 镜像，同时确认 Docker 服务、依赖下载和实际数据库连通。Node 版本以选定 Vite 的官方要求为准。 [本地开工冒烟](../README.md#本地开工冒烟) · [架构与基线](ARCHITECTURE.md#技术栈) · [Vite 初始化](https://vite.dev/guide/) · [Testcontainers 运行环境](https://java.testcontainers.org/supported_docker_environment/)
3. **只搭两端骨架和一条联调路径。** 保留 `delivery/` 放 Java，建议新建 `web/` 放 Vue 3、TypeScript 与 Vite。统一 `npm` 锁文件、配置示例、单一 API 客户端、会话读取与错误解析。后端先跑空库迁移和网点查询测试，前端先用同契约样例，身份就绪后通过代理读取实际返回。端口先核对占用，建议主联调前端 `5173`、后端 `8080`。MySQL 使用项目独立库和合成数据。
4. **固定一套可以复跑的数据。** 一个网点、东区和西区、两名配送员、一个操作员账号、一个调度账号、两位收件人。用保留前导零的合成运单做正常直派，另备一票地址待补分、一票需返站和一票属于另一收件人的对照。记录初始化方式和共享字段值，前后端样例从同一份契约取得 ID、枚举与状态。

**第一轮开工只看** [网点与运力 Spec](specs/station/0001-station-areas-and-capacity.md)、[数据库的网点与账号部分](DATABASE.md#网点运力账号)和[接口通用契约](ENGINEERING.md#通用契约)。首批只落网点、片区、规则、人员和在岗责任查询需要的表。后面每个 Spec 按自己实际使用的数据追加 Flyway 迁移。

## MVP 按依赖推进

工期是排期参考。进入下一行的条件是上一环已满足，能独立用契约样例验证的工作可以提前。每行交付时都要连上该阶段的页面和 API。

| --- | --- | --- | --- |

### 每个 Spec 内怎么做

1. 总管先写一页以内的 Ticket。列清本次业务结果、V1 范围、依赖的提交或接口、获准修改的路径、具体 API/DDL 和三条验收场景。优先锁定一条正常路径、一条拒绝路径、一条重复或故障路径。你确认关键契约后开始代码。
2. 后端 Agent 从入口写测试，保留预期失败记录，再用现有服务和迁移完成最小实现。状态写入口同时验响应及库里记录。前端 Agent 同步用同一份约定做页面、空状态和错误反馈，样例响应先随 Ticket 固定。
3. 后端跑过后把接口示例、启动命令、测试结果交给前端。前端切到真实 API，逐票用页面操作。总管合并前重跑受影响用例和失败路径。你亲自改一个条件再验一遍，例如把面单地址换成一个没有匹配规则的小区。 [交付评审](../.agents/skills/review-delivery/SKILL.md)

## 可以开几个 Agent

**推荐两名并行开发加一名按需验收，总管负责拆单与集成。** 从成功构建的共同基线起分工。还没有首个提交时，可先并行审表、核对接口样例和写非代码验收清单。

| 阶段 | Agent A · 后端关键路径 | Agent B · 前端 | Agent C · 独立工作或验收 |
| --- | --- | --- | --- |
| 骨架和入站 | Java 构建、单位与运力迁移、员工身份与实收写入。先完成大家共用的 Java 会话和模块结构。 | 建 Vue 与 Vite 骨架，按契约做登录、调度和分拣的样例页面。 | 审查验收样例；共享会话契约固定后，可做收件人登录独立任务。涉及共享身份文件的改动由同一所有者衔接。 |
| 发布和领件 | 顺序完成草案发布、授权、领件、投递和返站。由同一负责人合入共享履约写入口及锁顺序。 | 并行完成发布与配送页面，再接真实领件和返站接口。 | 可做收件人只读查询与 DTO，暂用固定履约时间线。等真实交接产生后接查件源数据，执行跨角色验收。 |
| MVP 验收后 | Java 权限、路线计算及 Redis 与 FastAPI 接口适配。 | 预计时段、位置不可用及客服体验。 | Python 纯计算与独立测试。估时联调通过后再接模型调用和评估。 |

- 一张 Ticket 对应一个工作分支和独立 worktree。同一台机器按任务配置独立端口及测试库，示例为 A 用 `8081` / `delivery_test_a`，B 用 `5174`，C 的 JVM 测试用 `8083` / `delivery_test_c`。使用 Compose 时按任务指定独立项目名；需要同时运行才分配宿主机端口。
- 总管维护基线提交、Flyway 编号及合并顺序。`pom.xml`、应用配置、Compose、前端锁文件和路由入口各指定一名维护者。只读工作可以共享接口快照，账号主体、库存写入口和迁移文件按所有者合并。
- 先合平台基线和稳定契约，再合数据提供方，最后合依赖它的页面与查件。总管用整合后的基线重新验证空库和已有数据升级。独立 worktree 通过的测试随当前任务记录，集成结果单独验收。

## 前后端联调步骤

1. 启动独立 MySQL，执行当前基线的 Flyway 迁移，加载固定演示数据。先从后端调用一条读接口和一条已实现的写接口，核对类型、错误与数据结果。
2. 前端开发服务器把相对路径 `/api` 代理到当前 Java 端口，浏览器通过前端同源入口访问。先取 CSRF 令牌并登录，登录后刷新令牌与会话信息。生产演示复用同源路径，前端构建产物和后端 API 由同一站点提供。 [Vite 开发代理](https://vite.dev/config/server-options.html#server-proxy)
3. 同一个界面先在样例数据上复现正常、空数据、权限拒绝、业务冲突和提交结果未知，再切换真实服务。用浏览器网络面板核对请求、响应、请求号和权限提示。连续扫码验焦点、前导零和回车。超时重试复用原幂等键。
4. 用同一票运单从操作员走到收件人。每次切换岗位用各自的有效会话。核对响应、页面和 MySQL 的关键状态及记录数。另开会话复现旧授权竞争与他人运单查询。问题记录发生步骤、输入、请求号、实际响应和已有记录，由对应所有者修正，再一起重跑。

## MVP 验收清单

- [ ] 用可复现的启动方式，从空库迁移并加载合成数据后，网点和收件人可分别登录并使用实际页面。
- [ ] 同一票件从实收、发布、扫码领件到实际送达，页面与数据库时间线一致。发布只建立授权，扫码接手才改变保管人。
- [ ] 重复扫码只产生一笔有效实收。地址匹配失败后能补分。本趟实际领件和发布竞争在真实 MySQL 中有可重复的验证结果。
- [ ] 失败样例先显示待返站，出发单位扫码收回后进入网点跟进。操作人和交接历史可查。
- [ ] 收件人只能查看本人的运单。会话失效和无权请求有明确提示，业务状态保持正确。
- [ ] 记录实际运行命令、用例数、结果、使用的基线提交、本人实测和待验证项。保存一份可演示的本地提交或标签。

## 开工时可以直接给总管的任务

> 按本路线图先做开工准备和 `station/0001` 的最小查询闭环。先报告仓库基线、Java/Node/Docker 状态。给我本次涉及的迁移、`GET /api/v1/staff/areas` 和当班人员查询契约，以及三条验收场景。说明查询如何在员工登录交付后接入正式权限。契约确认后，后端先写测试并实现，前端按同一份样例做查询页，最后切到真实数据联调。交付时给出命令、实际结果和我需要亲自验的一步。
