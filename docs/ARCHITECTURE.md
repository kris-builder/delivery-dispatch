## 整体架构

主业务采用一个 Spring Boot 应用、一个 MySQL 数据库和同源部署的 Web 前端。各模块维护自己的人员、计划、入站、领件和配送记录。实物状态以 MySQL 已提交状态为准。

| 层 | 职责 |
| --- | --- |
| Web 前端 | 提供网点操作页、驿站工作台、转运司机工作台、配送员工作台和收件人入口，通过同源 HTTP 接口访问业务。 |
| Spring Boot 应用 | 员工入口校验会话、岗位和业务权限。收件人入口核验登录身份和目标运单的归属，再读取该票可见数据。 |
| MySQL | 保存各模块的数据和操作记录。计划发布和领件授权在同一事务提交。 |

各模块之间的调用关系列在[模块依赖](MODULES.md#模块依赖)。

| 人员与配送计划 | Spring Boot、JDBC 和 MySQL 保存片区、班次、草案与调整记录。Java 按片区分组和匹配在岗的常规责任人。 |
| 扫码、查件与交接 | Java 校验业务状态。MySQL InnoDB 事务同时写状态和操作流水。趟次实领数按去重后的领件记录扣除装车回库。 |

| 在途查件 | 浏览器定位，Spring Boot 校验趟次后以 Redis String 保存最近位置并设置 TTL。高德 Web 服务按需提供道路距离和分段耗时。 [W3C 定位接口](https://www.w3.org/TR/geolocation/) · [Redis SET](https://redis.io/docs/latest/commands/set/) · [高德路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute) |

| 异常待办 | 履约结果和待办在同一个 MySQL 事务提交，网点工作台直接读取。 |
| 构建、迁移和验收 | Maven Wrapper 构建，Flyway 管理迁移，JUnit 和 Testcontainers 使用同一 MySQL 8.4 系列验证并发、回滚、空库迁移和已有业务数据升级。 |

## 履约写入与重试

- **入站分区。** 模拟运单资料提供结构化地址，网点与运力按本站的街道和小区规则匹配片区。履约保存实收与当前分区。自动匹配失败时保留实收，员工通过补分操作更新片区并追加记录。
- **状态校验。** 每个履约操作有固定的可执行状态及角色要求。后端确认当前状态、写入新状态、追加操作事件在一次数据库事务内完成。更正通过新的操作事件补记。
- **幂等。** 入站用网点与运单的唯一键配合状态校验。每笔可重试提交复用同一操作标识，已提交时返回原结果，遇到不同内容复用同一标识时提示冲突。合法的返站和重新领件走各自的操作入口。
- **更正。** 错录入站作废和片区更正追加事件，保留原记录和操作人。计划引用的包裹发生更正时，发布需重新校验版本。履约事件可按操作标识查到对应请求与交接流水。
- **异常放行与验收。** 缺单号用临时编号隔离，补齐后在同一事务保留原记录、核对唯一运单并更新放行状态。破损留证、收件人选择、各段实物交接和当面验收结果分别记录。后续交接继续引用已知破损凭证。
- **弱网。** 提交结果未知时，客户端以同一操作标识查询或重试。后续加入离线缓存时，界面把本地待提交与服务端已确认分别显示。收到补传后按当时的有效授权与实物状态决定是否接受。

## 计划发布与交接一致性

- **生成与修改草案。** 先读取网点直派件、配送片区、责任人和在岗人员，在写事务外分组。网点调度提交调整时，校验草案版本并在同一次提交记录调整与操作人。
- **确认发布。** 网点调度发布直派或分拨清单时，短事务核对计划版本、包裹版本与实际保管，以及拟领件人或目标驿站权限。同一包裹的直派与分拨授权互斥。投递约定变化时在同事务撤销已失效的未执行授权。
- **改派与转交。** 未领件改派将原授权撤销、新授权和变更流水一起提交。已领件先记录经调度确认的转交安排，实际交出与接收各自留事件。接手时重新核对当前保管和履约状态，再提交保管变更。原授权、逐步确认及最终结果都可按运单查询。
- **分拨交接。** 驿站模块持有应收清单及现场对账，履约依次写入网点交给转运司机及驿站实际接收。到站后，在同一批次提交中为正常件逐票写接收事件，为缺失、错件和破损件追加未签收差异。提交核对批次版本和角色权限，重试复用原结果。
- **驿站改上门。** 站长录入客户的上门服务时核对实物仍在本驿站，并与到站自取操作互斥。指派只改变领件授权，扫码更新实际保管。成功上门的交接、任务完成和计件凭证在同一事务提交，按任务唯一记账。
- **扫码领件。** 短事务锁定包裹并核对现行授权和在站状态，首笔成功扫码时建立趟次，写交接记录、实际趟次归属及实物状态。重新发布与扫码竞争时，以锁后状态判断。若 A 先扫码，旧草案发布冲突，包裹仍归 A。若新版先发布给 B，A 用旧授权扫码会收到冲突，该件仍在站等 B 领取。 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)
- **装车回库。** 工作台选择回库模式后扫描同一面单。履约在短事务里校验本人保管、网点、趟次及该件的投递状态，追加回库事件并恢复未出库。原领件记录保留，按回库后的交接状态计算本趟实领数。领件和回库都以操作标识重试，两个写入口使用相同的锁定顺序。后续趟次领件时检查现行授权。
- **配送异常。** 履约按上门服务和尝试标识保存失败事实并对重复提交去重。两次未妥投后，网点直派可按已确认的备用点位交接，驿站上门由驿站实际收回再跟进。收费续派须在事先告知并取得收件人同意后创建授权。同一服务换人或换趟沿用尝试记录。实物保管随真实交接变更。

撤销与重新发布、扫码领件与装车回库、返站与关趟的规则见[履约状态与计划发布](MODULES.md#履约状态与计划发布)，由对应规格确认和验收。

## 在途查件与估时的故障处理

- **停靠数据。** 跟随趟次记录经配送员确认的停靠顺序和版本。演示从合成资料读取停靠点坐标和参考停靠耗时。需要从实际地址取坐标时用地理编码，浏览器坐标对接高德时按坐标系转换。两项操作分别处理。 [高德地理编码](https://lbs.amap.com/api/webservice/guide/api/georegeo) · [高德坐标转换](https://lbs.amap.com/api/webservice/guide/api/convert)
- **最近位置。** 浏览器经 HTTPS 和本人授权上报当前趟次点位。Java 核验身份与趟次，按趟次在 Redis 保存坐标、采集时间、接收时间、精度和坐标系。仅当采集时间更新且点位仍新鲜时，才原子替换点位并刷新 TTL。位置过期或 Redis 不可用时，显示位置暂不可用。
- **剩余路程。** 以目标运单的当前趟次和已确认的停靠顺序为准，结合实际履约筛出目标前还需处理的站点。从最近有效位置出发，沿剩余站点累加到目标站的高德路段距离和耗时。按需算路，位置上报与基础查件各自完成。
- **预计送达。** Java 将到目标站的道路耗时和途中停靠数据交给 FastAPI，在业务写事务外计算。首版将道路耗时与前序停靠耗时相加，再输出预计时段。使用合成停靠耗时验算，积累可靠记录后用实际送达时间核对误差。点位过期、路段缺失、停靠顺序已变更或估时服务不可用时，页面仍可展示可用的履约进度。

## 异常待办与可靠投递

履约事件和异常待办在同一 MySQL 事务提交，四类内部工作台按职责读取。保存待办失败时整笔操作回滚。同一异常的超时、找回和赔付申请按异常状态与版本校验，重试按操作标识去重。找回时沿用原包裹标识并追加交接。

待退回清单按 MySQL 中的异常处理状态和截止时间查询。交接前重新核对实物在站、联系人跟进结果和异常版本。到期只改变待办分类，退回交接通过员工扫码确认。

跨系统可靠投递须先明确必达接收方、业务事件和送达要求，再定独立 Spec。若采用事务发件箱，验未提交回滚、应用重启和投递服务停机后补发、消费去重、持续失败可查询和重放、晚到事件处理，以及已提交履约记录可继续查询。当前站内待办由 MySQL 事务直接完成。

## 收件人授权与客服调用

收件人入口先通过 `identity` 取得有效会话中的收件人标识和已验证手机号。`tracking` 从 MySQL 查找可信运单资料中登记了该手机号的运单。按运单号添加、访问详情和咨询时同样校验运单归属。服务端读取同一份收件人可见履约数据，模型调用只接收必要状态、时间、网点公开说明和经处理的问题文本。模型的输入范围排除认证凭证、个人联系方式、完整地址、配送员精确位置和原始签收凭证。

调用在业务事务外完成，模型没有数据库、员工接口或履约写入权限。实际履约时间、预计时段和拨号入口由应用直接展示。应用根据授权运单的履约记录选择公开业务联系方式，联系方式无需传给模型。客服超时、缺少可核实事实或无法回答时，界面给出已知进度和人工联系入口。
