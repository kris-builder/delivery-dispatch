# 0001 扫码入站、自动分区与查件

Status: ready-for-agent

## 问题陈述

网点员工收到一批实物，需要确认本站实际收到哪些件，并在扫码时知道该把包裹放到哪个片区。重复扫码时实收数量必须对得上。地址缺失或没有匹配规则时，员工也需要先收件，再核对面单补分。客户来电时，网点要能按运单查到首次入站时间和当前片区。

## 解决方案

网点调度维护本网点的「街道 + 小区 → 片区」规则。演示用合成上游批次与运单明细。网点员工按批扫码核对实收、破损和无单号实物，正常件按地址分区，匹配不到的正常件由员工补分。

## 用户故事

1. 作为网点调度，我希望维护本站地址与片区的对应关系，以便员工扫件时能看到该放哪一堆。
2. 作为网点调度，我希望保存冲突规则时收到提示，以便避免同一地址被分到两个片区。
3. 作为网点员工，我希望能为这批到站件连续扫码，以便边收件边看到分堆结果。
4. 作为网点员工，我希望面单读不出时可核对后手工录入运单号，以便这票实物也能登记。
5. 作为网点员工，我希望同一票件被重复扫描时看到原入站记录，以便避免重复计数。
6. 作为网点员工，我希望能找到所有已经实收、仍待分配片区的件，以便集中核对和人工补分。
7. 作为网点员工，我希望按批次查实收、已分区和待分区数量，以便和现场收到的件对账。
8. 作为网点员工，我希望按运单号查首次入站时间、所在批次和当前片区，以便回答查件电话。
9. 作为网点调度，我希望看到已分区的在站件及仍待分区的件，以便按片区安排并明确哪些还需处理。
10. 作为网点调度，我希望能更正错误片区或作废错录入站，以便系统和现场实物重新对得上，同时保留原操作记录。

## 实现决定

- 网点与运力持有片区和地址匹配规则，提供查询、维护和匹配入口。每条规则以「网点、街道、小区」定位，指向一个本站有效片区。网点调度可以明确修改既有规则。同一地址键只能生效一条规则，录入冲突时提示核对。
- 接收上游提供的目标网点、批次和逐票应到运单明细。演示使用合成清单模拟上游，附带地址和必要的收件资料。导入只形成应到，员工扫码或人工确认后才记实收。运单号按字符串处理，保留前导零。
- 网点操作员在首次接收验货时登记破损或无可辨认单号，保存批次、发现时间、操作人和现场说明，可关联可用凭证。已识别的破损件挂原运单；无法识别时生成临时异常编号，补核到运单后追加关联。实物在网点隔离，异常先归上游交接待核，不进入正常配送或分拨。缺少实物的应到件在本批核对完成后另列未收。
- 缺单号由网点调度与上游核对，记录确认依据并将临时异常编号关联到真实运单。校验运单唯一与实物身份，重复提交只关联一次。核对通过且该票没有其他未解决的拦截事项时才放行，原临时记录仍可查。
- 网点操作员给破损件拍照，记录外包装与内件已确认的状况，并联系收件人。外包装破损时，收件人可以选择退回并交理赔处理，或者同意带异常标记继续送并当面检查。已确认内件破损时，通知收件人并登记待退回。继续送的件保留照片、客户确认和「待当面验收」标记。
- 包裹履约读取可信的登录网点及操作账号，校验批次归属。读取模拟地址后按街道和小区精确匹配，命中唯一有效片区时记录分区结果并返回名称。查无地址、没有有效规则或匹配结果无法确认时，将本件记为已入站、待分配片区，并给出待分配原因。
- MySQL 对包裹的「网点 + 运单号」建立唯一约束，每票只有一笔当前有效的首次入站记录。首次入站在同一事务保存批次、时间、分区结果与入站事件。重复扫码返回有效入站记录和当前片区。同一票并发扫码只产生一笔有效入站。
- 员工可为本站仍在站且待分区的件补分。错误片区由网点调度更正，目标片区须为本站有效片区。处于有效领件或分拨授权中的件，先撤销该件尚未执行的授权再更正。更新片区时追加操作人、时间和前后值，保留原入站时间与批次。网点调度修改规则后，已经实收的件保留已有分区。
- 网点调度可以对错录运单的有效入站追加作废记录，填写原因。同一事务将该笔从有效实收排除，保留原流水。仅允许作废尚未交接且没有现行领件或分拨授权的记录。该运单的真实包裹到站时，可沿同一包裹标识重新确认一笔有效实收。已有草案引用变更的包裹时，发布须重新校验包裹版本。
- 批次查询分别统计应到、已识别实收、无单号暂存、实收异常和应到未收。已识别的破损件只计一件实收，出现在异常明细。正常实收件按已确认的约定进入直派或驿站分拨。驿站接收沿用原包裹和运单，形成另一次交接。
- 使用 Vue 3 页面接收键盘式扫码枪输入或人工输入。Spring Boot 提供规则配置、连续入站、人工补分与查询入口，使用 Spring JDBC、Flyway 和 MySQL 8.4 LTS。错误提示区分重复扫码、待分区、规则冲突和权限问题。
- 网点员工进入扫码模式后，在同一页连续处理包裹。收到每票结果后更新分堆提示和件数，自动接收下一票，直到员工主动退出。正常件无需逐票点确认。重复扫码和待分区仍在同一页显示结果，不中断连续扫码。
- 演示按同一名员工边扫码边分堆处理。有效实收且成功匹配片区时计给扫码员工，待分区件在首次有效补分后计给补分员工。员工可查本人今日有效分拣数和逐票明细。重复扫码或更正片区不新增计件。错录实收作废时扣回对应计件，保留原运单、操作人、时间及作废原因。

## 测试决定

沿用 Spring Boot 和 MySQL Testcontainers 测试骨架。通过规则维护、扫码和查件的业务入口验收，核对返回结果和已提交数据。并发与回滚用真实 MySQL 验证，测试数据统一使用合成地址和账号。

| 场景 | 可验收结果 |
| --- | --- |
| 导入应到 A、B 两件，扫 A 后确认本批核对完成 | 扫描前应到 2、实收 0。核对完成后实收 1，B 列为应到未收。 |
| 上游到货时 A 外包装破损，另有一件缺失单号 | A 同时保留原运单实收与破损记录，缺单号件按临时异常编号隔离并可后续关联；两件均保留上游交接待核记录。 |
| 调度查到缺单号件的真实运单后放行，操作员重复提交关联 | 调度的核对、关联和放行可查，原异常记录保留，实收不重复计数。无授权操作员无法放行。 |
| 外包装破损的两票分别选择退回和继续送，另有一票确认内件破损 | 两票进入待退回，一票带照片和当面验收标记继续流转，三票的沟通与异常证据均可查。 |
| A 已入站，扫描没有匹配规则的 B，人工补到西区，再扫一次 A | 实收为 2，已分区为 2，待分区为 0。A 只有一笔入站记录，B 保留首次入站时间和人工补分记录。 |
| 扫描模拟资料查无地址或缺街道、小区的运单 | 仍可查到本站实收及待分区原因。人工选取本站有效片区后，可以按运单查当前片区。 |
| 网点调度提交同一地址指向两个片区的规则 | 页面提示配置冲突，原有效规则仍可查。 |
| 两名员工在不同批次同时扫同一票 | 仅有一笔入站事件，只有首次入站所属批次增加实收数。 |
| 保存包裹和入站事件其中一项失败 | 事务回滚，批次实收和运单查询保持提交前结果。 |
| 查看其他网点运单、用其他网点片区补分或由无维护权限的账号改规则 | 操作被拒绝或返回当前网点查无记录，数据保持原样。 |
| 网点调度把仍在站且无生效授权的 A 从错误片区更正为西区 | 实收与入站时间保持原值，当前片区改为西区，可查更正记录。 |
| 网点调度作废错录件 C，随后扫到真实的 C | 作废后扣减原批次有效实收；重扫后只存在一笔有效入站，原误录和作废事件均可核对。 |
| 网点调度试图作废已实物交接的记录，或更正仍有现行授权的包裹 | 操作返回冲突，实收、授权和实际持有人仍可查。 |
| 扫码枪发来的运单有前导零和回车后缀，下一件紧接着输入 | 运单号原值保留，连续扫码逐件显示结果。输入自动就绪，员工主动退出才结束。 |
| 员工今日计件为 86，连扫一件匹配成功的件、同一件的重复码和一件待分区件 | 计件变为 87，扫码模式一直保持。待分区件记录实收并提示待补分。错录的计件作废后扣回，明细可查原因。 |

## 范围之外

- 上游生产系统接入、责任结论与赔付、面单 OCR、地图围栏和模糊地址匹配。
- 配送计划发布、扫码出站、投递结果和收件人自助查询。
