# 0001 在途预计送达时段

Status: ready-for-agent

## 问题陈述

收件人需要知道包裹大概什么时候上门或到达代收点，以便安排收件。网点接到催件电话时，需要能解释预计还有多久，以及前面的停靠安排如何影响这票件。

## 解决方案

配送员实际领件后，在停靠顺序已确认、位置和路线都有效时为目标运单估时。Java 整理到目标站的道路耗时和前序站点，FastAPI 将行驶耗时与途中停靠耗时相加。收件人看预计时段，网点可以查预计耗时及其依据。包裹详情继续展示履约记录中的实际进度。

## 用户故事

1. 作为收件人，我希望看到大致的上门或到代收点时段，以便安排收件或取件。
2. 作为网点员工，我希望知道估计还要多久、前面还有几站以及估计更新时间，以便答复催件。
3. 作为网点员工，我希望配送员改变停靠顺序后，查到随新顺序更新的估计，以便按当前安排答复。
4. 作为收件人，我希望估时不可用时仍能查到当前进度，实际交接后能看到交接时间与去向。

## 实现决定

- Java 复用网点、驿站和本人运单的查件权限。网点直派和驿站上门按各自实际趟次估时。仅为已实际领走、目标站仍在本趟确认的待送顺序中、且路线与位置有效的件请求估时。目标站是约定上门地址或外部自取点。本站自取、装车回库、待返站及已经交接完毕的件展示各自履约事实。
- Java 从 `presence` 取本次算路时间、使用点位的采集时间、有效停靠顺序版本、目标之前未完成的停靠点，以及到目标站的道路行驶耗时。FastAPI 请求体只包含估时需要的时间、道路耗时和该计入的停靠数据。跨进程调用设置超时，在业务写事务之外完成。
- Python 将到目标站的道路行驶耗时与前序未完成站点的参考停靠耗时相加。首版演示使用可配置的每站 5 分钟，同一停靠点按一站计，目标站的预估到达时刻以本次算路时间加估计耗时得出。HTTP 请求校验时间与耗时字段，缺失或负数输入返回校验错误。
- FastAPI 返回估算的道路耗时、停靠耗时、总耗时、预计到达时间和对应时段。按网点本地时间划分，演示采用北京时间，凌晨 0 至 6 点、上午 6 至 12 点、下午 12 至 18 点、晚间 18 点至次日零点，边界计入新时段。跨日结果展示所对应的日期。
- 网点展示剩余站数、道路与停靠耗时、估计还要多久及更新时间。收件人详情及 AI 客服使用同一份预计时段，按已确认的投递方式显示预计上门或预计到指定自取点。
- Java 返回结果前复核运单仍可估时、所用点位仍有效，且停靠顺序与剩余站点仍匹配。改序、跳站或完成站点后，下一次估时用当前路线。路线过期、FastAPI 超时或结果失效时，页面展示已知进度和已有交接事实。实际交接时间与去向取自 MySQL 的履约记录。

## 测试决定

从 FastAPI 的 HTTP 入口用固定时刻和路线输入验收计算，再从网点查件及收件人详情入口核对展示、权限和降级。用合成账号、实际领件趟次样例及可控的在途和估时服务响应复演。评估时保留当时可用的输入，与同一票件的实际交接时间比对。

| 场景 | 可验收结果 |
| --- | --- |
| 14:00 算路，行驶需 35 分钟，前面 3 站各按 5 分钟 | 返回行驶 35 分钟、停靠 15 分钟、合计 50 分钟，预计 14:50。网点可见估算依据，收件人看到「预计下午上门」或「预计下午到代收点」。 |
| 目标前没有其他站，或估时字段缺失、耗时为负数 | 前序站为空时停靠耗时为零，仍按有效道路耗时计算。缺失或非法输入返回校验错误。 |
| 停靠顺序调整或目标件进入待返站，旧估时请求随后返回 | 旧结果不显示。仍在待送顺序时可按新路线估时，进入待返站时展示异常履约进度。 |
| 目标件未领走、点位过期、路线不可用或 FastAPI 超时 | 详情保留已知进度，仅在条件有效时显示预计时段。 |
| 算出的到达时刻跨过午夜 | 收件人看到对应日期和时段，网点仍可核对预计耗时。 |
| 代收点件预计 14:50 到达，实际 15:05 交给代收点 | 详情展示实际交接时间与「待领取」。验收用同一票的两个时间算出相差 15 分钟。 |
| 其他收件人查询此件，或外网点员工查询该运单 | 访问被拒绝，且该请求不会调用估时服务。 |

## 范围之外

- 未领件的出库前预测、自动排序、机器学习估时模型。
- 主动改派、派送承诺、预计时段通知的自动触发和发送。
